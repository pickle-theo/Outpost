# Outpost 迁移与回滚操作手册（V1.0）

> 适用：从自研 `cache_key_queue` / 「事务提交后异步删缓存」切换到 Outpost。
> 前置条件：已完成 [接入文档](接入文档.md) 的接入 Checklist，尤其「所有缓存 key 必须设置 TTL」。

## 0. 原则

1. **任何阶段都不会静默不删缓存**：白名单外的 namespace 由 `DirectCacheInvalidator` 在 `afterCommit` 同步 `DEL` 并打 WARN；`outpost.enabled=false` 时由业务原有删除逻辑负责。
2. **消息表永远与业务表同库同事务**，因此迁移过程中不存在「业务提交、消息未落库」的双写不一致窗口。
3. 每一步都有明确的准入/退出指标，指标不达标就地回滚到上一阶段。

## 1. 三阶段影子验证

### 阶段 0：基线采集（建议 ≥ 3 天）

- 采集：现有缓存删除成功率、脏缓存投诉/工单数、DB 读 QPS 与 P99、Redis QPS、业务事务耗时。
- 部署 Grafana 看板 `monitoring/grafana/outpost-dashboard.json`（8 个固定指标）。
- 由 DBA 执行 `scripts/ddl/outpost_message.sql` 建正式表，另建一张影子表（`outpost.table-prefix=shadow_` 对应 `shadow_message`，结构一致）。
- 退出条件：基线报表完成、告警阈值（`outpost.message.dead.gauge`、失败率、脏窗口）已评审。

### 阶段 1：影子写入（只写不投递，建议 ≥ 1 天）

配置：

```yaml
outpost:
  enabled: true
  table-prefix: shadow_
  auto-create-table: false
  schedule:
    enabled: false      # 关闭调度，消息只落库不投递
  cleanup:
    enabled: false
```

- 验证项：
  - 业务事务回滚后 `shadow_message` 无残留；
  - `REQUIRES_NEW` 内层提交的消息独立存在；
  - 单事务消息数、`bizKey=namespace:cacheKey`、`payload=cacheKey`、双删两条消息的 `message_type` / `max_retry` / `next_retry_time` 正确；
  - 无事务注册立即抛异常，且未产生消息。
- 用 `scripts/shadow-reconcile.sh` 对账业务变更日志与影子消息表，输出「漏注册」「重复注册」「字段不一致」三类差异。
- 退出条件：对账差异为 0（或全部差异可解释）、生产 INSERT 异常数为 0、`outpost.message.produce.total` 与业务变更数一致。

### 阶段 2：灰度切流（按 namespace 逐步放量）

```yaml
outpost:
  table-prefix: outpost_
  schedule:
    enabled: true
  delivery-cache:
    enabled-namespaces: [low_risk_config]   # 白名单内走消息表，其余回落同步直删
```

放量顺序建议：`low_risk_config` → 1 个读多写少业务域 → 10% → 50% → 100%。每档至少观察一个完整业务周期（含一次高峰期）。

- 观察：`outpost.message.delivery.success.total` / `fail.total`、`outpost.schedule.duration.ms`、`outpost.delivery.duration.ms`、`outpost.message.dead.gauge`、`outpost.message.redelivery.ratio`、DB 读 QPS（检查击穿）。
- 回滚触发（任一命中即回退上一档）：
  - 死信持续新增且 30 分钟内未收敛；
  - 投递失败率 > 基线 2 倍且持续 10 分钟；
  - DB 读 QPS / P99 相对基线上升超过评审阈值（击穿）；
  - 脏缓存投诉数上升；
  - `redelivery.ratio` 持续 > 5%（说明 `processing-timeout` 或 `batch-size` 不合理）。
- 退出条件：100% 白名单（或直接清空 `enabled-namespaces`）稳定运行 ≥ 3 天，全部指标在阈值内。

### 阶段 3：全量与旧链路下线

1. 清空 `outpost.delivery-cache.enabled-namespaces`（空 = 全部走消息表）。
2. 开启 `outpost.cleanup.enabled=true`（SUCCESS 保留 3 天、DEAD 保留 30 天）。
3. 观察 3 天后，停用旧 `cache_key_queue` 生产者（保留消费者做兜底 7 天）。
4. 再观察 7 天无异常后，下线旧队列与其监控。

## 2. Drain 流程（计划内停机 / 下线 SDK）

> 目标：把在途消息全部投递完，不丢任何一条缓存失效。

1. **停止新消息注册**：业务发版切回原有删缓存逻辑，或把灰度白名单收窄到空集以外的回落下线方案（注意白名单外仍会同步直删，不会静默跳过）。此时**不要**设置 `outpost.enabled=false`，否则调度器一并停止。
2. **等待在途归零**：

```sql
SELECT status, COUNT(*) AS cnt FROM outpost_message
WHERE message_type = 0 AND status IN (0, 1, 3)
GROUP BY status;
-- 期望：无结果（0 行）
```

   同时确认 `outpost.message.dead.gauge` 不再增长。
3. **处理死信**：用 `OutpostAdminService.queryDeadMessages(...)` 导出死信，人工确认后 `resendMessage` / `batchResendMessages` 重发；确认全部回到 `SUCCESS`。
4. **停止调度**：逐个实例设置 `outpost.schedule.enabled=false` 并滚动重启，或直接 `outpost.enabled=false` 停机。
5. **保留数据**：消息表至少保留 30 天（清理任务只删 SUCCESS/DEAD，`FAILED`/`PROCESSING` 不会自动清理，需人工确认后处理），用于回灌与审计。
6. **资产清理**：确认无需回灌后再下线表与 Grafana 看板。

## 3. 紧急回灌

适用场景：消息表被误删/数据丢失、某段时间生产写入异常导致消息缺失、需要补删一批脏缓存。

1. **冻结**：暂停相关业务的缓存失效写入（或把受影响 namespace 从白名单移出，走同步直删兜底），避免回灌与实时消息交织。
2. **确定范围**：从业务变更日志/审计表确定 `[since, until]` 与 namespace。
3. **生成回灌消息**：执行 `scripts/replay.sh`（内部调用 `scripts/backfill.sql`），把业务变更日志转成 `cache_delete` / `cache_tag_delete` 消息；脚本支持 `SINCE` / `UNTIL` / `NAMESPACE` / `BIZ_TYPE` / `MAX_RETRY` 环境变量。
4. **校验**：

```sql
SELECT COUNT(*) FROM outpost_message WHERE trace_id = 'backfill';
SELECT biz_type, status, COUNT(*) FROM outpost_message
WHERE trace_id = 'backfill' GROUP BY biz_type, status;
```

   条数必须与业务变更数一致，且全部 `status=0`、`retry_count=0`、`next_retry_time <= NOW()`。
5. **开启消费**：确认调度器运行、Redis 正常，观察 `outpost.message.delivery.success.total` 上升、`fail.total` 不增长。
6. **对账**：用 `scripts/shadow-reconcile.sh` 复核无漏删。
7. **解冻**：恢复业务写入与正常灰度配置。

> 回灌消息是普通消息（`message_type=0`），失败会正常退避并可能在重试耗尽后进入死信；务必确认 `DeliveryHandler` 幂等。

## 4. 回滚到旧链路

| 场景 | 动作 | 影响 |
| --- | --- | --- |
| 投递大面积失败 | 把 `enabled-namespaces` 收窄回上一档（其余回落同步直删 + WARN），或临时 `outpost.enabled=false` 并启用旧删缓存逻辑 | 不会静默不删；在途消息由 Drain 处理 |
| Redis 长时间不可用 | 调度器自动降级为无锁逐条 CAS，但缓存删除仍会失败并退避；超过阈值则回滚到同步直删 | 需监控 `delivery.fail.total` 与死信 |
| DB 消息表异常 | 停止生产注册，执行 Drain；必要时用回灌脚本补齐 | 保留业务表数据，消息表可重建 |
| SDK 自身缺陷 | `outpost.enabled=false` 一键关闭全部装配，应用正常启动 | 需业务侧原有删缓存逻辑兜底 |

## 5. 变更记录模板

每次灰度/回灌记录：时间、操作人、配置 diff、涉及 namespace、影响行数、8 个指标的前后对比、回滚决策与结果。
