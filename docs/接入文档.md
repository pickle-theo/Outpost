# Outpost 接入文档（V1.0）

> 适用版本：`1.0.0-SNAPSHOT`。本文是接入方必须逐项确认的契约说明；与设计文档冲突时以 `.trae/specs/build-outpost-outbox-sdk/spec.md` 及其「显式偏差说明」为准。

## 1. 能力边界

Outpost 是一个**通用 Transactional Outbox**：保证的是最终一致性——业务事务提交成功后，注册在同一事务里的消息一定落库，调度器持续重试投递直到成功或进入死信。它用一张 `outpost_message` 表换取可靠性。

**缓存一致性只是内置的第一种业务场景，不是能力边界**。注册、调度、抢占、退避、死信、清理、运维、指标全链路都与 `bizType` 无关；任意幂等的异步动作都可通过 `DeliveryHandler` 接入，见 §1.1。

V1.0 内置能力：

- 通用业务消息入口：`registerMessage` / `registerDelayedMessage` / `@OutboxMessage` + 自定义 `DeliveryHandler`（见 §1.1）
- 编程式 `OutpostTemplate` 与注解式 `@OutboxMessage` / `@OutboxCache`
- 事务内聚合、`beforeCommit` 批量 INSERT、`afterCompletion` 无条件清理
- 分布式锁调度（`redis` / `local`；连续 3 轮加锁失败降级为无锁逐条 CAS）
- 批量抢占、影响行数不匹配按 id 重查、`PROCESSING` 超时重置
- 指数退避（1s/3s/10s/30s/60s/300s）、死信治理、辅助消息（延迟双删第二次）
- 内置 `cache_delete`（DEL）与 `cache_tag_delete`（原生 rockscache Lua）处理器
- `RockscacheReadClient` 弱一致读客户端（仅 `read-client=builtin`）
- 清理任务、Micrometer 指标、`OutpostAdminService` 运维 Java API

### 1.1 通用业务消息（非缓存场景）

**定位**：`registerCacheInvalidate` / `@OutboxCache` / `enabled-namespaces` 灰度 / 延迟双删 / `message_type=1` 辅助消息 / 两个内置处理器（`cache_delete`、`cache_tag_delete`）都属于缓存便捷层；通用场景请使用下列入口，不要依赖缓存配置组。

| 能力 | 通用入口 |
| --- | --- |
| 编程式注册 | `OutpostTemplate.registerMessage(bizType, bizKey, payload)` |
| 延迟消息 | `OutpostTemplate.registerDelayedMessage(bizType, bizKey, payload, delayMills)` |
| 显式事务 | `OutpostTemplate.executeInTransaction(Supplier<T>)` |
| 注解式注册 | `@OutboxMessage(bizType, bizKey, payload, delayMills)`（SpEL） |
| 消费 | 实现 `DeliveryHandler` 并注册为 Spring Bean |

**典型场景**：MQ / 领域事件投递、外部 HTTP 回调与 Webhook、搜索索引或物化视图重建、短信邮件推送、异步补偿任务、延迟触发的定时任务。

**接入三步**

1. 选一个全局唯一的 `bizType`。`DeliveryHandlerRegistry` 在启动期拒绝重复注册，且不得与 `cache_delete` / `cache_tag_delete` 冲突。
2. 在事务最外层注册消息。`payload` 是字符串（默认上限 65536 字节），序列化由业务负责；`bizKey` 建议用业务唯一键，供业务侧做幂等去重。

```java
outpostTemplate.executeInTransaction(() -> {
    jdbcTemplate.update("UPDATE orders SET status = ? WHERE id = ?", "PAID", orderId);
    outpostTemplate.registerMessage("order_paid", orderId, "{\"orderId\":\"" + orderId + "\"}");
    return null;
});
```

```java
@Transactional
@OutboxMessage(bizType = "order_paid", bizKey = "#orderId", payload = "#orderId")
public void pay(String orderId) {
    // 业务 SQL
}
```

3. 实现幂等的处理器。抛出 `UnrecoverableDeliveryException` 表示永远不可能成功（直接进死信、`dead_reason=2`），其它异常走阶梯退避。

```java
@Bean
public DeliveryHandler orderPaidHandler() {
    return new DeliveryHandler() {
        @Override
        public String getBizType() {
            return "order_paid";
        }

        @Override
        public void deliver(OutboxDeliveryMessage message) throws Exception {
            eventPublisher.publish(message.getBizKey(), message.getPayload());
        }

        @Override
        public long getMaxExecutionMillis() {
            return 3000L;
        }
    };
}
```

**慢调用必须声明耗时上界**：`getMaxExecutionMillis()` 默认 1000ms，参与启动期 `processing-timeout-seconds ≥ 10 × 最大耗时` 与 §4.4 耦合公式校验。外部 HTTP / 批量索引类 handler 若不重写，启动会直接失败，或运行期被 `processing-timeout` 反复重置造成重复投递。

**纯通用场景可以完全不依赖 Redis**：

```yaml
outpost:
  enabled: true
  delivery-cache:
    enabled: false       # 关闭内置缓存处理器、读客户端与灰度回落
  schedule:
    lock-type: local     # 单实例部署
```

| `outpost.schedule.lock-type` | 实现 | 适用 | 是否需要 `StringRedisTemplate` |
| --- | --- | --- | --- |
| `redis`（默认） | `RedisDistributedLock`（`SET NX PX` + Lua 解锁） | 多实例生产部署 | 是 |
| `local` | `LocalDistributedLock`（进程内 `ReentrantLock`，忽略锁 TTL） | 单实例、本地调试、纯通用场景 | 否 |

启动期仅在「`delivery-cache.enabled=true` 或 `lock-type=redis` 且未提供自定义 `DistributedLock`」时才强制校验 `StringRedisTemplate`，避免纯通用接入被无谓的 Redis 依赖卡住。

> **多实例警示**：`local` 锁只在单 JVM 内有效。多副本部署必须使用 `redis`，否则各实例会重复扫表；逐条 CAS 能保证单条消息只被一个实例抢占，但超时重置仍可能造成重复投递，**handler 幂等是硬要求**。基于数据库表的 `jdbc` 锁需要新增表，V1 不提供。

**配置隔离说明（V1 限制）**：目前 `batch-size` / `core-size` / `queue-capacity` / `processing-timeout-seconds` / `max-retry-count` / `backoff-steps` 仍是全局值，所有 `bizType` 共用一个投递线程池，耦合公式取所有 handler 中的最大耗时。若混跑慢调用与快调用，需按最慢 handler 统一配置，或先拆分应用实例；按 `bizType` 的独立配额与线程池隔离属于后续版本规划。

## 2. 不支持清单（必须确认）

| 不支持项 | 说明与替代方案 |
| --- | --- |
| **强一致性** | 不保证「事务提交后缓存立即一致」，只保证最终执行。存在秒级脏窗口；需要强一致读请使用业务侧读写主库或分布式锁，不要依赖本 SDK |
| **本地缓存（进程内缓存）失效** | 仅失效 Redis。Caffeine / Guava / Ehcache 等本地缓存需业务自行广播或改用短 TTL |
| **跨库 / 跨服务事务** | 消息表与业务表必须**同一个数据库、同一个 `DataSource` bean 实例、同一个事务**。跨库写入请用 MQ / DTM 等方案 |
| **消息顺序性** | 按 `next_retry_time, id` 扫描、并发投递、失败重试、超时重置都会打乱顺序。业务不得依赖消息先后顺序 |
| **通用幂等屏障** | SDK 不提供 barrier 表或去重中间件。投递可能重复（超时重置、锁过期），**handler 必须天然幂等**（`DEL`、`TagAsDeleted` 均幂等） |
| **NESTED savepoint 内消息撤销** | V1.0 不实现回滚到 savepoint 时清理该作用域消息。**接入约束：消息注册必须位于事务最外层**；`REQUIRES_NEW` 独立作用域仍支持 |
| **rockscache `StrongConsistency` 强一致读** | `RockscacheReadClient` 只实现弱一致 Fetch（命中失效时立即返回旧值 + 异步回源），不支持阻塞等待回源的强一致读 |

其他边界：

- 不提供事务消息的顺序投递、延迟任意时长调度（仅按 `next_retry_time` 扫描）、消息内容二进制（payload 为字符串）、内置 HTTP 运维端点。
- 死信保留 30 天、成功消息保留 3 天后由清理任务删除；`FAILED` / `PROCESSING` 永不自动清理。
- tag 模式下不支持延迟双删（启动期强制关闭并打 WARN）。

## 3. 事务与数据源约束

注册前 SDK 会强制校验 `TransactionSynchronizationManager.isSynchronizationActive() && isActualTransactionActive() && hasResource(dataSource)`，任一不满足立即抛 `IllegalStateException`（告警日志全局只打一次，但每次调用都抛异常）。

- 业务方法与消息注册必须在同一个 `@Transactional` 方法内，且**注解切面位于事务通知内层**（SDK 切面使用 `LOWEST_PRECEDENCE`）。
- 多数据源场景：为业务主库标记 `@Primary`，或提供 `OutpostDataSourceProvider` bean 显式指定；多个 DataSource 且无唯一 `@Primary` 会导致**启动失败**。
- 生产路径 INSERT 异常向上传播，业务事务随之回滚，不做吞噬。
- `payload` 超过 `max-payload-bytes`（默认 65536 字节）直接抛异常，不截断；单事务消息数超过 `batch-register-threshold`（默认 200）分批插入并打 WARN。

## 4. `delete` 与 `rockscache_tag` 选型对比

> 配置值：`outpost.delivery-cache.handler-type = cache_delete | cache_tag_delete`。

| 维度 | `cache_delete`（DEL） | `cache_tag_delete`（TagAsDeleted） |
| --- | --- | --- |
| 写侧动作 | `DEL key`，物理删除 | Redis Hash：`HSET lockUntil 0`、`HDEL lockOwner`、`EXPIRE delay` |
| 读侧要求 | 无改造，普通 `GET` / `SET` 即可 | **必须改造为 hash 语义**（内置 `RockscacheReadClient` 或已有兼容实现）；普通 `GET` 会 `WRONGTYPE` |
| 写回竞态 | 「删除之后到达的旧回源写回」可能复活脏值，需延迟双删兜底 | 锁 + `lockOwner` 校验从算法层消除，旧值不会覆盖新值 |
| 延迟双删 | 支持（每个 key 注册 1 条普通 + 1 条辅助消息） | 不支持，启动期强制关闭并打 WARN |
| 缓存击穿 | **删除后到回源完成之间会击穿 DB**（见接入 Checklist 第 1 条） | 命中失效时立即返回旧值并异步回源，天然不击穿 |
| 消息量 | 开启双删时 ×2 | ×1 |
| 额外配置 | 无 | `tag.read-client` **必填**；`tag.delay-seconds`（默认 10）、`tag.lock-expire-millis`、`tag.lock-sleep-millis`、`tag.empty-expire-seconds`、`tag.random-expire-adjustment` |
| 适用场景 | 读路径无法改造、缓存 key 已全部设置 TTL、可接受秒级击穿与双删 | 可接受读路径改造、希望一套机制解决击穿与写回竞态 |

### 4.1 读路径改造要求（tag 模式）

- `read-client=builtin`：SDK 装配 `RockscacheReadClient`，业务用 `fetch(key, expireSeconds, loader)` / `fetchBatch(keys, expireSeconds, batchLoader)` 替换原缓存读；`rawGet` / `rawSet` 仅供运维排查。
- `read-client=external`：业务已有兼容实现（如 Go 服务或自研 Java 版），SDK 不装配读侧。**必须自行保证写侧 Hash 协议一致**（字段 `value` / `lockUntil` / `lockOwner`，`lockUntil` 为秒级时间戳）。
- **缺失 `read-client` 时启动直接失败**，不会出现「写侧写 hash、读侧普通 GET」的静默 `WRONGTYPE`。
- 灰度回落 `enabled-namespaces` 白名单外的 namespace 走 `DirectCacheInvalidator`（`afterCommit` 同步 `DEL`）：整 key 删除后读侧按 miss 回源，对 tag 读路径同样安全，不会出现类型冲突。

### 4.2 Redis 超时

所有内置 Redis 操作受 `outpost.delivery-cache.redis-timeout-ms`（默认 1000）约束；超时抛 `RedisOperationTimeoutException`，按**可重试失败**进入退避，不吞异常。

## 5. 关键配置速查

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `outpost.enabled` | `true` | `false` 时不装配任何 Outpost bean |
| `outpost.table-prefix` | `outpost_` | 白名单 `^[A-Za-z0-9_]{0,32}$`，非法值启动失败 |
| `outpost.auto-create-table` | `false` | 关闭且表不存在时，**首次写入**抛明确异常提示执行 DDL |
| `outpost.max-payload-bytes` | `65536` | 超限抛异常 |
| `outpost.delivery-cache.enabled` | `true` | `false` 时关闭全部内置缓存处理器与缓存便捷层 |
| `outpost.schedule.type` | `redis-lock` | 无匹配 `OutpostScheduler` 实现时启动失败 |
| `outpost.schedule.lock-type` | `redis` | `redis` / `local`，决定 `DistributedLock` 实现，非法值启动失败 |
| `outpost.schedule.fixed-delay-ms` | `5000` | 必须 ≥ 100 |
| `outpost.schedule.batch-size` | `100` | 区间 [1, 1000]，受热更耦合公式校验 |
| `outpost.schedule.processing-timeout-seconds` | `300` | 需 ≥ 10 × handler 最大执行耗时 |
| `outpost.schedule.queue-capacity` | `1000` | 必须 ≥ 10 × batch-size |
| `outpost.retry.backoff-steps` | `1,3,10,30,60,300` | 严格单调递增，否则启动失败 |
| `outpost.retry.max-retry-count` | `10` | |
| `outpost.delivery-cache.enabled-namespaces` | 空 | 空 = 全部走消息表；非空时白名单外回落同步直删并打 WARN |
| `outpost.cleanup.enabled` | `true` | SUCCESS 保留 3 天、DEAD 保留 30 天 |

启动期 8 项强制校验（数据源唯一、bizType 唯一、超时/耗时、耦合公式、参数区间、退避单调、队列容量、锁类型）任一失败都会**抛异常终止启动**，不会只打 WARN。

## 6. 接入 Checklist

> **1. 【最高优先级】`cache_delete` 处理器会击穿缓存，且所有缓存 key 必须设置 TTL。**
> `DEL` 之后到回源完成之间的并发读会直接打到 DB；若某个 key 没有 TTL 且删除动作最终丢失（Redis 长时间不可用、死信未处理、人工误操作），脏值会**永久残留**。上线前必须：为每一个缓存 key 设置合理 TTL（兜底最终过期）、评估热点 key 击穿并加互斥回源/限流，或改用 `cache_tag_delete` 模式。这一条是 V1.0 接入的硬性前置条件。

- [ ] 已执行 DBA 审核后的 DDL（`scripts/ddl/outpost_message.sql`），或明确在非生产环境启用 `auto-create-table`
- [ ] 消息表与业务表使用同一个数据库、同一个 `DataSource` bean 实例；多数据源已配置 `@Primary` 或 `OutpostDataSourceProvider`
- [ ] 所有注册消息的方法位于事务最外层，未使用 NESTED savepoint 包裹消息注册
- [ ] 所有缓存 key 已设置 TTL；热点 key 已评估击穿风险并有兜底
- [ ] 已选定 `cache_delete` 或 `cache_tag_delete`；如选 tag 模式，读路径已改造为 hash 语义并显式配置 `tag.read-client`
- [ ] 已确认 `DeliveryHandler` 幂等，且 `bizType` 全局唯一（重复会启动失败）
- [ ] 通用业务消息场景已选定锁类型：单实例可用 `lock-type=local` 去掉 Redis，多实例必须用 `redis`；慢调用已重写 `getMaxExecutionMillis()`
- [ ] 已注册死信告警处理：`DeadMessageListener`、按 `dead_reason` 分流的日志通道（`1` 运维 / `2` 业务）可接入告警系统
- [ ] 已配置 Grafana 看板（8 个固定指标，见 `monitoring/grafana/outpost-dashboard.json`）与 `outpost.message.dead.gauge` 告警阈值
- [ ] 已验证「业务回滚后消息不落库」「无事务注册立即抛异常」
- [ ] 已确认 `processing-timeout-seconds`、`batch-size × 单条耗时 / core-size < processing-timeout × 0.5` 满足业务实际耗时
- [ ] 已阅读并确认「不支持清单」全部 7 项不会与业务诉求冲突
- [ ] 已按 `docs/迁移与回滚手册.md` 完成三阶段影子验证，具备 Drain 与紧急回灌能力

## 7. 运维与观测速查

```java
// 查询与重发（默认过滤辅助消息）
OutpostPage<OutboxDeliveryMessage> page = adminService.queryMessages(new MessageQuery());
adminService.resendMessage(deadMessageId);
OutpostStats stats = adminService.getStats();

// 仅以下配置支持热更，其余修改必须重启
adminService.updateConfig(new OutpostConfig()
        .set(OutpostConfig.BACKOFF_STEPS, new long[]{1, 3, 10})
        .set(OutpostConfig.ENABLED_NAMESPACES, Arrays.asList("order"))
        .set(OutpostConfig.CLEANUP_ENABLED, true)
        .set(OutpostConfig.DOUBLE_DELETE_ENABLED, false)
        .set(OutpostConfig.DOUBLE_DELETE_DELAY_MILLIS, 1000L)
        .set(OutpostConfig.BATCH_SIZE, 100));
```

8 个固定指标名（Prometheus 导出时 `.` 转为 `_`）：

`outpost.message.produce.total`、`outpost.message.delivery.success.total`、`outpost.message.delivery.fail.total`、`outpost.message.dead.gauge`、`outpost.message.redelivery.ratio`、`outpost.schedule.duration.ms`、`outpost.delivery.duration.ms`、`outpost.retry.count.distribution`。

## 8. 常见故障

| 现象 | 排查方向 |
| --- | --- |
| 启动失败，提示耦合公式 | 增大 `processing-timeout-seconds` / `core-size`，或减小 `batch-size`；公式为 `batch-size × 单条耗时 / core-size < processing-timeout × 0.5` |
| 「当前方法无事务上下文」 | 方法缺 `@Transactional`；或业务事务绑定的 DataSource 与 SDK 解析到的不是同一 bean 实例 |
| 首次写入提示执行 DDL | 未建表且 `auto-create-table=false`，执行 `scripts/ddl/outpost_message.sql` |
| tag 模式读缓存 `WRONGTYPE` | 读侧仍在用普通 `GET`，改用 `RockscacheReadClient` 或兼容实现 |
| 消息重复投递 | 超时重置 / 锁过期属预期行为，确认 handler 幂等；用 `deliver_attempt` 量化 |
| 辅助消息停在 `FAILED` | 延迟双删第二次失败按设计停在此终态，不计死信、不告警；主消息成功即可 |

## 9. 兼容性矩阵

| 环境 | 结论 | 验证方式 |
| --- | --- | --- |
| JDK 8 字节码 | 源码以 `--release 8` 编译 | 三模块 `pom.xml` 的 `maven.compiler.release=8` |
| JDK 17+ 测试 | 通过 | 本机 JDK 21 运行全部单元测试 |
| Spring Boot 2.3.12.RELEASE | 通过 | `.\mvnw.cmd -Pboot23 clean test` |
| Spring Boot 2.7.18（默认） | 通过 | `.\mvnw.cmd clean install` |
| Spring Boot 3.x | **运行时不兼容，V1 不发布** | 仅提供 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 声明 |

Boot 3 不兼容的具体原因（V2 待办）：

1. Spring Framework 6 移除了 `JdbcTemplate` 的 `queryForObject(String, Class<T>, Object...)`、`query(String, RowMapper<T>, Object...)`、`queryForList(String, Class<T>, Object...)`、`update(String, Object...)` 旧重载，仓储层需改为显式 `PreparedStatementSetter` / `RowMapper` 写法。
2. Boot 3 要求 JDK 17 与 Jakarta 命名空间；本 SDK 编译目标为 JDK 8。
3. `spring.factories` 在 Boot 3 中不再用于自动配置导入，故同时提供 `AutoConfiguration.imports`；但当前类使用 Boot 2.x 的 `@Configuration` 而非 `@AutoConfiguration`，仅保证声明存在。

静态检查：全部主源码中除 JDK 自带的 `javax.sql.DataSource` 外，无 `javax.*` / `jakarta.*` 引用。
